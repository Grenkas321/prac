# Путеводитель по коду «Мафии»

Здесь описан каждый файл проекта:
- что он делает;
- на каких строках какие части;
- почему каждая часть сделана именно так (и какие были альтернативы);
- какие средства языка и библиотеки внутри используются.

Номера строк — на 2026-10-05. Ссылки кликабельны в VS Code и на GitHub.

**Как читать.** Код идёт снизу вверх по зависимостям:
1. `core` — ни от чего не зависит;
2. модель игры `game/types, state, protocol`;
3. роли `roles`;
4. движки `engine`;
5. правила и ведущий `game/*`;
6. журналы, командная строка, ИИ, `main`;
7. сборка и тесты.

**Сквозная идея**, которая объясняет большинство решений: **у каждого изменяемого объекта ровно один писатель.**
- **`GameState`** меняет только ведущий в главной нити.
- **Игрок** получает неизменяемый снимок и личную сводку, а отвечает сообщением.
- **Объект `Player`** меняет только его собственная нить.
- **Синхронизация** — в одном месте: в движке, вызов «разослать и дождаться всех».

Поэтому мьютексов в игровой логике нет, а ThreadSanitizer гонок не находит.

# 1. `src/core` — инфраструктура

## [src/core/shared_ptr.hpp](../src/core/shared_ptr.hpp) — свой `shared_ptr`

**Что делает.** Умный указатель с подсчётом ссылок, который хранит все общие объекты проекта: состояние, снимки, игроков, почтовые ящики. Это пункт 1 задания. Файл только заголовочный: шаблоны должны быть видны в месте использования.

**Устройство.** `SharedPtr<T>` = указатель на объект `ptr_` + указатель на управляющий блок `block_` ([278-279](../src/core/shared_ptr.hpp#L278-L279)). В блоке лежат атомарный счётчик и способ уничтожить объект.

| Строки | Часть | Почему так |
|---|---|---|
| [28-64](../src/core/shared_ptr.hpp#L28-L64) | `ControlBlock` — абстрактный блок | Тип объекта и удалителя **стёрт**: у всех `SharedPtr<T>` один тип блока, поэтому `SharedPtr<Dog>` можно превратить в `SharedPtr<Animal>`, и удалится всё равно `Dog`. Виртуальный `destroy_object()` знает настоящий тип. |
| [36-38](../src/core/shared_ptr.hpp#L36-L38) | `add_ref` — `fetch_add(relaxed)` | Новый владелец появляется только копированием существующего: счётчик ≥ 1 и обнулиться не может. Упорядочивать нечего, нужна только атомарность. `relaxed` — самый дешёвый вариант. |
| [44-49](../src/core/shared_ptr.hpp#L44-L49) | `release` — `fetch_sub(acq_rel)` | **release**-часть «публикует» записи в объект, сделанные этим владельцем. **acquire**-часть даёт последнему владельцу увидеть записи всех остальных, прежде чем он запустит деструктор. Без этого деструктор мог бы читать недописанные данные из другой нити. |
| [46-47](../src/core/shared_ptr.hpp#L46-L47) | `destroy_object(); delete this;` | Два шага: сначала объект, потом память блока. Блок удаляет себя сам — его деструктор защищённый ([58](../src/core/shared_ptr.hpp#L58)), снаружи удалить нельзя. |
| [63](../src/core/shared_ptr.hpp#L63) | `atomic<long> owners_{1}` | Блок рождается вместе с первым владельцем. Так `make_shared_ptr` не делает лишний `+1`. |
| [68-71](../src/core/shared_ptr.hpp#L68-L71) | `DefaultDelete<U>` | Свой, а не `std::default_delete`: `<memory>` намеренно не подключается — по заданию указатель свой. Удаляет через `U*`, «родной» тип. |
| [74-85](../src/core/shared_ptr.hpp#L74-L85) | `PointerBlock<U, D>` | Для конструктора от сырого указателя: хранит `U*` и удалитель. `[[no_unique_address]]` ([84](../src/core/shared_ptr.hpp#L84)) — пустой удалитель (лямбда без захвата) не занимает памяти. |
| [88-109](../src/core/shared_ptr.hpp#L88-L109) | `InplaceBlock<T>` | Для `make_shared_ptr`: объект лежит **внутри** блока — одно выделение памяти вместо двух. Объект в `union` ([106-108](../src/core/shared_ptr.hpp#L106-L108)), чтобы компилятор не вызывал его конструктор и деструктор сам. Создаём размещающим `new` ([93](../src/core/shared_ptr.hpp#L93)), уничтожаем явным `~T()` ([102](../src/core/shared_ptr.hpp#L102)). Деструктор блока пустой ([97](../src/core/shared_ptr.hpp#L97)): объект к тому моменту уже уничтожен. |
| [131-132](../src/core/shared_ptr.hpp#L131-L132) | пустые конструкторы | `constexpr`, `noexcept`; блока нет, `use_count() == 0`. |
| [136-155](../src/core/shared_ptr.hpp#L136-L155) | от сырого указателя (и с удалителем) | `requires is_convertible_v<U*, T*>` — концепт-ограничение: принимаем наследника. Если `new` блока бросил исключение, объект удаляется сразу ([150-153](../src/core/shared_ptr.hpp#L150-L153)), иначе утечка. Нулевой указатель даёт пустой `SharedPtr`, удалитель не вызывается. |
| [158-170](../src/core/shared_ptr.hpp#L158-L170) | копирование (и наследник → база) | Ещё один владелец: `add_ref`. |
| [173-179](../src/core/shared_ptr.hpp#L173-L179) | перемещение | Владелец тот же, сменилась переменная — счётчик не трогаем. `std::exchange` забирает указатель и обнуляет источник одной строкой. |
| [182-186](../src/core/shared_ptr.hpp#L182-L186) | деструктор | `release()`; последний владелец всё удалит. |
| [191-218](../src/core/shared_ptr.hpp#L191-L218) | присваивания | Идиома **copy-and-swap**: скопировать во временный, обменяться, временный умрёт со старым значением. Сначала +1 новому, потом −1 старому. Поэтому безопасны `a = a` и `a = a->next`, где старый объект сам владеет источником. |
| [221-233](../src/core/shared_ptr.hpp#L221-L233) | `reset` (три формы) | Те же присваивания из нового временного. |
| [235-240](../src/core/shared_ptr.hpp#L235-L240) | `swap` (метод и свободная функция) | Свободная — чтобы работал `using std::swap; swap(a, b)` и находилась через ADL. |
| [244-246](../src/core/shared_ptr.hpp#L244-L246) | `get`, `*`, `->` | Два вида разыменования, как требует задание. Константность «поверхностная», как у сырого указателя. |
| [249](../src/core/shared_ptr.hpp#L249) | `explicit operator bool` | `if (p)` работает, а `int n = p` или `p + 1` — нет. |
| [267-272](../src/core/shared_ptr.hpp#L267-L272) | aliasing-конструктор (закрытый) | Общий блок, но смотрим через другой адрес. На нём построены приведения. |
| [284-286](../src/core/shared_ptr.hpp#L284-L286) | `make_shared_ptr` | Variadic-шаблон и `std::forward` — идеальная передача аргументов в конструктор `T`. |
| [289-301](../src/core/shared_ptr.hpp#L289-L301) | `static_pointer_cast`, `dynamic_pointer_cast` | Результат делит блок с исходным: объект удалится один раз. Неудачный `dynamic_cast` даёт пустой указатель. |
| [305-323](../src/core/shared_ptr.hpp#L305-L323) | сравнения `==`, `<=>`, с `nullptr` | C++20: `!=`, `<`, `>=` компилятор выводит из `==` и `<=>` сам. `std::compare_three_way` даёт корректный полный порядок указателей. |
| [329-334](../src/core/shared_ptr.hpp#L329-L334) | `std::hash` | Специализация в `namespace std` — можно класть в `unordered_set`. Хеш по адресу, согласован с `==`. |

**Не поддерживается** (сознательно, [9](../src/core/shared_ptr.hpp#L9)): `weak_ptr` — циклов владения в проекте нет; массивы `T[]`; `SharedPtr<void>`.

**Используется внутри:** `<atomic>` и порядки памяти, размещающий `new`, `union` с нетривиальным членом, `requires`-ограничения, `[[no_unique_address]]`, `<=>`, `std::exchange`, `std::forward`.

## [src/core/random.hpp](../src/core/random.hpp) / [random.cpp](../src/core/random.cpp) — генератор `Rng`

**Что делает.** Псевдослучайные числа с явным зерном: одно зерно — одна и та же партия на любом компьютере.

**Почему не `std::mt19937` + `std::uniform_int_distribution`.** Сам `mt19937` детерминирован, а вот алгоритмы распределений (`uniform_int_distribution`, `shuffle`) стандарт не фиксирует. В libstdc++ и libc++ они дают разные числа, и партия по зерну на другой платформе не повторится. Поэтому и генератор, и все распределения свои.

| Строки | Часть | Почему так |
|---|---|---|
| [random.cpp:15-20](../src/core/random.cpp#L15-L20) | `splitmix64` | Разворачивает одно 64-битное зерно в четыре хорошо перемешанных слова состояния. Даже зерно 0 даёт ненулевое состояние. Так рекомендуют авторы xoshiro. |
| [random.cpp:22-26](../src/core/random.cpp#L22-L26) | конструктор от зерна | Четыре вызова `splitmix64`. |
| [random.cpp:46-56](../src/core/random.cpp#L46-L56) | `next()` — xoshiro256** | Эталонный алгоритм: быстрый, 256 бит состояния, хорошее качество. Сверяется с эталонными значениями в `test_random`. |
| [random.cpp:62-73](../src/core/random.cpp#L62-L73) | `below(n)` без смещения | Наивное `next() % n` чаще даёт малые числа, если 2^64 не делится на n. Отбрасываем «хвост» длиной `(0 - n) % n` (это 2^64 mod n в беззнаковой арифметике). Цикл почти всегда делает один шаг. |
| [random.cpp:75-85](../src/core/random.cpp#L75-L85) | `uniform_int(lo, hi)` | Ширину считаем в беззнаковых: `hi - lo` в знаковых может переполниться (это UB). |
| [random.cpp:88-90](../src/core/random.cpp#L88-L90) | `uniform_real()` | 53 старших бита — ровно мантисса `double`; умножение на 2^-53 точное. |
| [random.cpp:96-104](../src/core/random.cpp#L96-L104) | `chance(p)` | «Монета» с краевыми случаями p ≤ 0 и p ≥ 1. |
| [random.hpp:72-79](../src/core/random.hpp#L72-L79) | `shuffle` — Фишер — Йетс | Свой, потому что алгоритм `std::shuffle` не зафиксирован стандартом. |
| [random.cpp:107-122](../src/core/random.cpp#L107-L122) | `jump()` — прыжок на 2^128 шагов | Эталонный многочлен прыжка. Даёт **независимые потоки**, которые гарантированно не пересекаются. |
| [random.cpp:28-34](../src/core/random.cpp#L28-L34) | `stream(seed, k)` | k прыжков от общего зерна. Договорённость ([random.hpp:11](../src/core/random.hpp#L11)): поток 0 — ведущий, i+1 — игрок i, n+1 — выбор ИИ-мест. Поэтому решения одного игрока не зависят от того, сколько чисел вытянули другие и в каком порядке отвечали нити — ключ к одинаковым партиям на двух движках. |

**Не потокобезопасен намеренно** ([random.hpp:13](../src/core/random.hpp#L13)): у каждой нити свой экземпляр, общего нет.

**Используется внутри:** битовые операции, беззнаковая арифметика по модулю 2^64, `std::array`, шестнадцатеричный литерал `double` (`0x1.0p-53`).

Три файла — только данные и чистые функции над ними, без поведения. Разделены по тому, **кто видит данные**:

# 3. Роли: `src/roles`

**Устройство в двух словах:**
- **Базовый класс `Player`** — всё общее для любой роли: обработка запроса, дневное поведение, выбор цели.
- **Наследники** добавляют только особенности своей роли.
- **Ночной ход и приём тайных сведений** — обычные (не виртуальные) методы `act()` и `learn()`. Их подключает фабрика, проверяя тип **концептами при компиляции**.
- **Логики потоков в ролях нет вообще.** `handle()` — обычный вызов «запрос → ответ»; какая нить его вызывает, решает движок.

**Почему и виртуальные методы, и концепты.** Это разные вопросы:
- **Виртуальный метод** отвечает «как именно делать», если делают все: голос, речь, оценка цели. Ведущий работает с `SharedPtr<Player>` и не знает конкретного типа.
- **Концепт** отвечает «есть ли способность вообще», и отвечает **при компиляции**. Мирному нельзя случайно «приделать» ночной ход: базовый класс вообще не имеет `act()`.

## [src/roles/beliefs.hpp](../src/roles/beliefs.hpp) / [beliefs.cpp](../src/roles/beliefs.cpp) — «мозг» бота

**Что делает.** По публичной истории и своему знанию вычисляет оценки каждого игрока:
- **подозрение** — похож ли на мафию;
- **доверие** — можно ли верить его словам;
- **опасность** для моей команды;
- **давление** — как сильно он нападает на подозреваемых.

**Главное решение** ([beliefs.hpp:9-12](../src/roles/beliefs.hpp#L9-L12)): оценки **не копятся**, а каждый раз считаются с нуля по всей истории. Это чистая функция.
- Новое раскрытие («выбыл — оказался мафией») сразу переосмысливает все прошлые события: кто его защищал, кто голосовал вместе с ним.
- Нет состояния, которое могло бы разойтись с историей.
- Цена — время, поэтому шаг 3 ниже оптимизирован.

# 4. Движки: `src/engine` — как исполняются игроки

## [src/engine/engine.hpp](../src/engine/engine.hpp) — интерфейс

Четыре операции:
- `start(players)` — запустить;
- `exchange(requests)` — разослать и дождаться всех ответов;
- `stop()` — остановить;
- `name()` — название.

| Строки | Часть | Почему так |
|---|---|---|
| [24-30](../src/engine/engine.hpp#L24-L30) | `exchange` | **Главное решение проекта.** «Разослать пакет и дождаться ВСЕХ» — это **барьер фазы**: к возврату каждый адресат закончил `handle()`, и всё, что он сделал, видно ведущему. Ответы идут **в порядке запросов**, а не в порядке готовности: поэтому исход не зависит от планировщика ОС. Исключение игрока перебрасывается, но только после того, как ответили остальные — барьер держится и при ошибке. |
| [3-4](../src/engine/engine.hpp#L3-L4) | ведущий знает только интерфейс | Нити или корутины — правилам всё равно. Второй движок добавлен, не тронув ни ведущего, ни игроков. |

**Альтернатива, от которой отказались:** «каждый игрок сам пишет в общее состояние под мьютексом». Тогда порядок записей зависел бы от планировщика, партия по зерну не повторялась бы, и мьютексы расползлись бы по всем правилам.

## [src/engine/thread_engine.hpp](../src/engine/thread_engine.hpp) / [thread_engine.cpp](../src/engine/thread_engine.cpp) — нить на игрока (пункт 2 задания)

**Что общее между нитями и чем защищено** — в шапке файла ([thread_engine.hpp:8-14](../src/engine/thread_engine.hpp#L8-L14)):
- почтовый ящик — под мьютексом;
- снимок — неизменяем;
- счётчики `SharedPtr` — атомарные;
- `Player` трогает только своя нить;
- `GameState` в нити не попадает вовсе.

| Строки | Часть | Почему так |
|---|---|---|
| [thread_engine.hpp:44-47](../src/engine/thread_engine.hpp#L44-L47) | `Job{request, promise<Response>}` | Запрос и «обещание ответа». `std::promise` / `std::future` передают ответ **или исключение** между нитями и дают синхронизацию (happens-before) без ручных флагов. |
| [thread_engine.hpp:51-56](../src/engine/thread_engine.hpp#L51-L56) | `Mailbox{mutex, condition_variable, optional<Job>, stopping}` | Почтовый ящик — единственное, что делят ведущий и нить игрока, поэтому только он под мьютексом. Не больше одного задания за фазу. |
| [thread_engine.cpp:15-35](../src/engine/thread_engine.cpp#L15-L35) | `start` | **Долгоживущие** нити: создаются один раз на партию, а не на каждый запрос. Создание нити — дорогая системная операция, а ходов за партию тысячи. Нить получает копии `SharedPtr` игрока и ящика: они живут, пока жива нить. Создание `std::thread` синхронизировано с началом её функции, поэтому нить видит игрока полностью собранным. |
| [thread_engine.cpp:37-60](../src/engine/thread_engine.cpp#L37-L60) | `worker_loop` | Нить спит на `condition_variable` (не крутится в пустом цикле — тест `engine` это проверяет). Предикат в `wait` ([44](../src/engine/thread_engine.cpp#L44)) защищает от ложных пробуждений и от пропущенного `notify`. Ответ считается **без** мьютекса. Исключение не убивает нить (иначе `std::terminate`): оно передаётся через `set_exception`. |
| [thread_engine.cpp:62-114](../src/engine/thread_engine.cpp#L62-L114) | `exchange` | Сначала проверка всего пакета, чтобы не разослать половину и упасть. Затем рассылка: задание кладётся под мьютексом, `notify_one` — **после** снятия блокировки, чтобы проснувшаяся нить не упёрлась в занятый мьютекс. Затем `future::get()` по порядку запросов. |
| [thread_engine.cpp:116-131](../src/engine/thread_engine.cpp#L116-L131), [9-13](../src/engine/thread_engine.cpp#L9-L13) | `stop`, деструктор | Флаг остановки, затем `join` всех нитей. Деструктор зовёт `stop()`, в том числе при раскрутке стека после исключения: `std::thread` в состоянии joinable при уничтожении вызвал бы `std::terminate`. |

**Используется внутри:** `std::thread`, `std::mutex`, `std::lock_guard` / `unique_lock`, `std::condition_variable`, `std::promise` / `std::future`, `std::exception_ptr`.

| [coro_engine.cpp:9-24](../src/engine/coro_engine.cpp#L9-L24) | `player_loop` — тело корутины | Цикл: `co_await` следующего запроса → `handle()` → `co_yield` ответа. `co_yield` внутри `catch` запрещён языком, поэтому исключение сначала запоминается, потом отдаётся ([18-22](../src/engine/coro_engine.cpp#L18-L22)). ## [src/engine/console_engine.hpp](../src/engine/console_engine.hpp) / [console_engine.cpp](../src/engine/console_engine.cpp) — пользователь за столом (`--interactive`, пункт 2 задания)

**Что делает.** Оборачивает любой движок. Запрос на место пользователя не уходит боту: обёртка печатает подсказку ведущего и читает ответ из консоли. Остальные запросы передаются внутреннему движку.

**Почему обёртка, а не класс «игрок-человек»:**
- Пользователю может достаться любая из 40 ролей, и ему нужны ровно те же запросы, что боту этой роли.
- Запрос уже содержит всё нужное: допустимые цели и действия, снимок, личную сводку.
- Поэтому ни ведущий, ни роли не меняются, и режим работает и с нитями, и с корутинами.

Альтернатива — наследник `Player` с консольным вводом — потребовала бы своего класса на каждую роль или особой ветки в каждом ночном ходе.

# 5. Правила: `voting`, `night`, `night_rules`, `victory`

**Общее решение:** все правила — **чистые функции**. Состояния нет, нитей нет, на входе всё нужное, на выходе итог. Поэтому:
- их можно тестировать напрямую, без запуска партии (`test_night`, `test_victory`, `test_extra_roles`);
- итог не зависит от того, в каком порядке пришли ходы;
- применяет итог только ведущий — единственный писатель состояния.

## [src/game/night_rules.hpp](../src/game/night_rules.hpp) / [night_rules.cpp](../src/game/night_rules.cpp) — полная ночь со всеми ролями

**Вход:** состояние и **все** принятые ходы. **Выход:** отчёт `NightReport` ([night_rules.hpp:40-58](../src/game/night_rules.hpp#L40-L58)) — кто погибнет утром, кто спасён, кто что узнал, кто сядет в тюрьму, что объявить всем. Функция ничего не меняет: отчёт применяет ведущий.

**Почему конвейер этапов** ([night_rules.hpp:1-18](../src/game/night_rules.hpp#L1-L18)). Порядок ходов на входе ни на что не влияет; порядок задают этапы, и каждый зависит только от предыдущих:
- блокировка должна снять ход **до** того, как защита сработает;
- оговор — **до** проверки;
- сведения — **после** нападений, чтобы Каттани знал, кто убит этой ночью.

## [tests/test_framework.hpp](../tests/test_framework.hpp) — свой мини-фреймворк
Внешние библиотеки (GoogleTest и т.п.) запрещены.
- **`test::run(имя, функция)`** запускает случай. Исключение тоже считается провалом.
- **`CHECK(условие)`** не прерывает случай: печатаются все провалы сразу, с файлом и строкой.
- **`test::finish()`** возвращает код 0 или 1 — так его понимают `make test` и `ctest`.
- `inline`-переменные ([18-20](../tests/test_framework.hpp#L18-L20)) делают заголовок самодостаточным, без `.cpp`.

## [tests/fake_llm_server.hpp](../tests/fake_llm_server.hpp) и [tools/fake_llm_server.cpp](../tools/fake_llm_server.cpp) — поддельный сервис модели

- **Сервер** слушает только `127.0.0.1` на свободном порту, который выбирает ядро. Обслуживает соединения в своей нити и отвечает в форматах OpenAI и Anthropic.
- **Очередь сценариев**: свой код и тело, свой текст модели, задержка (для проверки таймаута), обрыв без ответа, мусор вместо HTTP. Пустая очередь — «умный» корректный ответ по заданию из промпта.
- **Запись запросов**: каждый принятый запрос сохраняется (путь, заголовки, тело), поэтому тест видит, что ушло в сеть, — например, что ключ был только в заголовке.
- **`send(…, MSG_NOSIGNAL)`**: клиент мог уйти по таймауту, и без этого флага сервер получил бы `SIGPIPE`.
- **Инструмент для ручной проверки** `tools/fake_llm_server` (`make fake-server`) — тот же сервер на заданном порту. Печатает каждый запрос и сообщает, был ли передан ключ, не показывая его.
