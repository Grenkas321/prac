# Шпаргалка к защите

Все команды запускаются из корня проекта в WSL/Linux. Перед защитой один раз:

```sh
make check        # -Werror-сборка, программа, 21 тест, они же под TSan (~7 мин с нуля)
```

Номера строк актуальны на момент сдачи (2026-10-03).

## 3. Вопросы и короткие ответы

### Счётчик ссылок

**Как устроен `SharedPtr`?**
- Два поля: указатель на объект `ptr_` и указатель на управляющий блок `block_`.
- В блоке лежит атомарный счётчик владельцев и виртуальный `destroy_object()`.
- `make_shared_ptr` кладёт объект прямо в блок (`InplaceBlock`) — одно выделение памяти вместо двух.

**Почему счётчик атомарный, а не под мьютексом?**
Копии одного указателя живут в разных нитях: снимок, например, читают все игроки. Атомарного `fetch_add`/`fetch_sub` достаточно, и он без блокировки.

**Почему увеличение `relaxed`, а уменьшение `acq_rel`?**
- **Увеличение.** Тот, кто копирует, уже владеет ссылкой: объект гарантированно жив. Упорядочивать ничего не нужно, важна только атомарность.
- **Уменьшение.** Последний владелец удаляет объект. Ему нужно увидеть все записи в объект, которые сделали другие владельцы до своего освобождения. Для этого их `release` синхронизируется с его `acquire`.

**Кто удаляет блок?**
Сам блок, в `release`: когда счётчик дошёл до нуля, он вызывает `destroy_object()` (удалитель или `~T()`), затем `delete this`. Деструктор блока защищённый — снаружи его не удалить.

**Как работает `dynamic_pointer_cast`?**
Через aliasing-конструктор ([268](../src/core/shared_ptr.hpp#L268)): новый указатель держит **тот же** блок, но смотрит на приведённый адрес. Счётчик общий, поэтому объект удаляется один раз.

**Что не поддерживается?**
`weak_ptr` (циклов владения в проекте нет), `T[]`, `SharedPtr<void>`.

**Самоприсваивание?**
Через копию и `swap`: старое значение отпускается после того, как новое уже захвачено. Это безопасно; тест «самоприсваивание» это проверяет.

### Почему на состоянии игры нет мьютекса

**Кто меняет `GameState`?**
Только ведущий, и только из главной нити. У состояния один писатель.

**Что получают игроки?**
`Request` с `SharedPtr<const PublicSnapshot>` — копией публичного состояния, которая после создания не меняется — и личной сводкой `Briefing`.
- Неизменяемое читать из многих нитей можно без блокировок.
- Ролей других игроков в снимке нет: их там нет по построению, а не потому, что их отфильтровали.

**Где синхронизация?**
`Engine::exchange` — «разослать и дождаться всех». Это барьер фазы:
- запрос передаётся через почтовый ящик под мьютексом;
- ответ возвращается через `promise`/`future`, что даёт отношение happens-before.

Пока игроки думают, ведущий ничего не меняет — он ждёт. Когда ведущий меняет состояние, никто из игроков не работает.

**Объект `Player` разве не общий?**
Его меняет только своя нить: она вызывает `handle`. У объекта тоже один писатель.

**Чем это доказано?**
`make tsan`: все тесты, включая массовый на нитях, проходят под ThreadSanitizer.

**Где мьютексы всё же есть?**
- почтовый ящик нити (`ThreadEngine`);
- журнал диалога с ИИ: в него пишут нити нескольких ИИ-игроков;
- лимит обращений к ИИ — вместо мьютекса атомарный CAS.

### Порядок разрешения ночи

**Почему «сначала собрать, потом разрешить»?**
Ходы приходят из разных нитей в произвольном порядке. Если применять их по мере поступления, исход зависел бы от планировщика. Например: доктор успел ответить раньше мафии — жертва спасена, позже — нет. Поэтому ведущий собирает всё одним пакетом ([host.cpp:1033-1038](../src/game/host.cpp#L1033-L1038)) и отдаёт его чистой функции `resolve_full_night`.

**Как собираются ходы?**
1. Совет мафии: каждый мафиози голосует, побеждает большинство. При равенстве решает Босс — старший живой мафиози. См. `decide_mafia`, [night.cpp:10](../src/game/night.cpp#L10).
2. Способности остальных ролей.

**Порядок этапов** ([night_rules.cpp:26-38](../src/game/night_rules.cpp#L26-L38)):
1. **Кража хода** (жулик): кто чей ход совершает.
2. **Блокировки** (пьяница, вор, тюрьма, заморозка): чьи ходы отменены.
3. **Оговор** (баламут): кто этой ночью покажется мафией.
4. **Защиты** (доктор, телохранитель, самурай).
5. **Нападения** (мафия, комиссар, маньяк, киллер, …) с учётом защит.
6. **Сведения**: проверки и наблюдения — после нападений, поэтому Каттани знает, кто убит этой ночью.
7. **Итог**: гибель по собственным правилам ролей (Блейд, отравитель, камикадзе).

**Почему именно так?**
Каждый этап зависит только от предыдущих: блокировка должна отменить защиту до того, как защита сработает; оговор — до проверки.

**Когда объявляются смерти?**
Утром ([host.cpp:1076](../src/game/host.cpp#L1076)): ночь только формирует `pending_deaths_`. Закрытые объявления — только «мафия / не мафия», спасения не объявляются. Открытые — ещё роль, кем убит (роль нападавшего из `NightReport::killed_by`) и «на N напали, но его спасли».

### Условия победы

Функция `judge` — [victory.cpp:28-49](../src/game/victory.cpp#L28-L49). Обозначения: M — мафия, C — мирные, X — одиночки-убийцы.

| Состав живых | Итог |
|---|---|
| никого нет | ничья |
| M = 0 и X = 0 | победа мирных |
| M = 0, X = 1, C ≤ 1 | победа маньяка |
| M > C + X | победа мафии |
| M = C + X и X = 0 | победа мафии (паритет) |
| иначе | игра продолжается |

**Почему маньяк считается отдельно?**
Он не мафия и не мирный, а третья сторона. По заданию мирные не побеждают, пока он жив. При M = C + X с живым маньяком игра продолжается (правило 5 для мафии).

**Почему проверка дважды за круг?**
Состав меняется в двух местах: после казни и утром (ночные смерти). Конец нужно поймать сразу, иначе следующая фаза пройдёт с уже решённым исходом. См. [host.cpp:292, 308](../src/game/host.cpp#L292).

**Ничья по пределу?**
Да, после 317 дней ([host.cpp:1245](../src/game/host.cpp#L1245); значение — `HostConfig::max_days`, [host.hpp:43](../src/game/host.hpp#L43)) — защита от бесконечной партии.

**Нейтральные (хакер, жулик)?**
Не считаются ни в одной из сторон.

### Разница движков

| | `ThreadEngine` | `CoroEngine` |
|---|---|---|
| исполнение | долгоживущая `std::thread` на игрока; спит на `condition_variable` | корутина на игрока; всё в одной нити |
| запрос | кладётся в почтовый ящик под мьютексом, `notify_one` | кладётся в канал, ведущий делает `resume()` |
| ответ | `promise::set_value` → `future::get` | `co_yield` кладёт ответ в канал и приостанавливает корутину |
| параллельность | да: голоса и ночные ходы считаются одновременно | нет, по очереди |
| исключение игрока | `set_exception`, перебрасывается в главной нити | ловится в корутине, отдаётся через `co_yield`, перебрасывается |
| нитей при N = 10 | 11 | 1 |

**Почему партии побайтно совпадают?**
- Решение игрока зависит только от его `Request` и его собственного генератора `Rng::stream(seed, id+1)`, но не от времени и не от порядка других нитей.
- `exchange` возвращает ответы в порядке запросов, а не в порядке прихода.

Тесты `coro_engine` и `mass` сравнивают протоколы целиком.

**Зачем два движка?**
- Нити — обязательная часть задания.
- Корутины — дополнительный пункт: пошаговая симуляция без блокировок. Отлаживать удобно, потому что всё в одной нити.

Интерфейс общий (`Engine`: `start`, `exchange`, `stop`, `name`), поэтому ни ведущий, ни игроки о движке не знают.

**Что значит, что `await_suspend` возвращает `bool`?**
`false` означает «не засыпать»: запрос уже лежит в канале, и корутина продолжает выполнение сразу, без лишнего возврата к движку.

**Кто владеет кадром корутины?**
`PlayerTask`: он перемещается, но не копируется, и в деструкторе вызывает `destroy()`. `final_suspend` возвращает `suspend_always`, поэтому кадр не исчезает сам.

### Прочее, что могут спросить

- **Как гарантируется одна партия на одно зерно?**
  - Свой генератор xoshiro256**; результат `std::uniform_int_distribution` стандарт не фиксирует, у разных библиотек он разный.
  - Поток 0 — ведущий, поток i+1 — игрок i; ИИ-места выбираются потоком n+1.
- **Как боты принимают решения?**
  - На каждом запросе оценки (подозрение, доверие, опасность) заново пересчитываются по всей публичной истории.
  - Раскрытие роли «переписывает» прошлое: голоса против оказавшегося мафией становятся заслугой.
  - Мафия подставляет тех, кого и так подозревает город.
- **Распределение побед?**
  - База, 288 партий: мирные 35 %, мафия 33 %, маньяк 28 %, ничьи 4 %.
  - С доп. ролями: мирные 57 %, мафия 29 %, маньяк и отравитель 13 %.
- **Что если игрок ответил недопустимо?**
  Ведущий проверяет ответ (`is_valid_answer`, [voting.cpp:77](../src/game/voting.cpp#L77)) и переспрашивает — до трёх раз (`kMaxAttempts`, [host.cpp:23](../src/game/host.cpp#L23)). Если и после этого ответ недопустим, ответа нет: голос не засчитывается, ход пропускается.
- **Что если API модели недоступен?**
  Любая ошибка (сеть, код ответа, формат, недопустимая цель, лимит) возвращает «совета нет», и игрок решает эвристикой. Тест: партия с мёртвым сервисом побайтно совпадает с обычной.

## 4. Пользователь за столом и объявления — вопросы

- **Как устроен `--interactive`?**
  Обёртка над движком (`ConsoleEngine`). В каждом пакете `exchange` запрос на место пользователя не уходит боту: печатается подсказка ведущего и читается ответ. Остальные запросы — внутреннему движку. Ответ пользователя вставляется на место его запроса: порядок ответов тот же.
- **Почему не класс «игрок-человек»?**
  Пользователю может достаться любая из 40 ролей. Запрос уже содержит допустимые цели и действия, снимок и личную сводку — ровно то, что нужно для ответа. Ни ведущий, ни роли не менялись, режим работает и с нитями, и с корутинами.
- **Что видит пользователь?**
  Общий протокол, как все за столом, и **только свои** сведения: роль, союзников (если мафия), свои проверки. Роль печатается только ему в консоль ([host.cpp:219-230](../src/game/host.cpp#L219-L230)), в историю и журнал не попадает.
- **Как выбирается место?**
  `--seat N` или по зерну отдельным потоком `n+2`, поэтому раздача и ходы ботов не меняются. ИИ это место не отдаётся.
- **А если ввод неверный или закончился?**
  Неверный — «Не понял: …» и переспрос. Конец ввода (Ctrl+D, EOF) — дальше решает бот его роли. Тест: партия без ввода совпадает с обычной партией.
- **Корутины и пользователь?**
  `ConsoleEngine` оборачивает и `CoroEngine`: корутины ботов возобновляются, а ход пользователя читается в той же нити ведущего.
- **Открытые и закрытые объявления — в чём разница в коде?**
  Одна функция `disclose` ([host.cpp:527](../src/game/host.cpp#L527)): `is_mafia` всегда, роль — только при открытых. Убийца — из ночного отчёта (`killed_by`), спасённые — `saved`. При закрытых это не печатается и не попадает в историю: проверено тестом `announcements`.
- **Чем открытые объявления влияют на ботов?**
  Объявленная роль — достоверное знание. Например, голос против казнённого маньяка засчитывается как «попадание» ([beliefs.cpp:89-93](../src/roles/beliefs.cpp#L89-L93)).
